# Backup Integrity Verification

This document describes how Stellar Nebula Nomad backups are created, verified, reported on, and drilled. It covers the standalone verifier (`scripts/verify-backup.sh`), the CI workflow (`.github/workflows/backup.yml`), and the Prometheus alerts that consume the generated status files.

## 1. Backup process overview

`scripts/backup.sh` produces one compressed archive per run:

```
backups/
  nebula_backup_<YYYYmmdd_HHMMSS>.tar.gz
  backup.log
  backup-validation-report.md     # generated by verify-backup.sh
  backup-validation.json          # generated by verify-backup.sh
  backup_status.prom              # generated by verify-backup.sh
```

Archive layout (relative paths inside the tarball):

```
nebula_backup_<timestamp>/
  metadata/contract_info.json     # network, contract id, RPC URL, backup version
  state/contract_state.json       # Horizon latest ledger snapshot
  state/latest_ledger.json
  state/horizon_contract.json     # when CONTRACT_ID is set
  state/contract.wasm             # when the Stellar CLI is available
  state/snapshots/*.json          # ledgers, effects, operations, transactions, retention
  verification/checksums.txt      # sha256sum of every file except itself
```

The flow is: prerequisites → directory setup → Horizon/WASM exports → state snapshots → checksum generation → `tar.gz` compression → integrity verification → optional off-chain upload (S3/IPFS) → retention cleanup → notification.

Key environment variables: `BACKUP_DIR`, `STELLAR_NETWORK`, `CONTRACT_ID`, `RPC_URL`, `HORIZON_URL`, `RETENTION_DAYS`, `S3_BUCKET`, `IPFS_UPLOAD`, `WEBHOOK_URL`.

### Backup script modes

```bash
./scripts/backup.sh                              # normal daily backup
./scripts/backup.sh --test-restore               # backup + restore test + verifier dry run
./scripts/backup.sh --schedule                   # install a 02:00 UTC cron entry
./scripts/backup.sh --verify-only <archive.tar.gz>  # verify an existing archive only, then exit
```

`--verify-only` never creates a backup. It calls `scripts/verify-backup.sh` when available and otherwise falls back to a built-in check (`gzip -t`, `tar -tzf`, extraction, checksum verification, required-file presence). This mode is intended for CI and ad-hoc audits.

## 2. Verification checks

`scripts/verify-backup.sh` performs these checks in order. Every check is recorded as `pass` or `fail` with a human-readable detail string. A failure in any check makes the overall status `fail` and the script exit code `1`.

| Check | What it validates |
| --- | --- |
| `archive_exists` / `archive_readable` | The path exists and is readable |
| `archive_format` | Filename ends in `.tar.gz` or `.tgz` |
| `archive_nonempty` | Archive size is greater than zero bytes |
| `gzip_integrity` | `gzip -t` succeeds (compressed stream is intact) |
| `tar_listing` | `tar -tzf` can list the archive |
| `sane_file_count` | Entry count is between 3 and 100,000 |
| `path_safety` | No absolute paths or `..` traversal entries |
| `extraction` | Archive extracts cleanly into a local staging directory |
| `backup_structure` | A backup root with `verification/` and `metadata/` is found (handles both a top-level backup directory and a flat layout) |
| `checksums_present` | `verification/checksums.txt` exists and is non-empty — **a missing file is a failure, never silently skipped** |
| `checksums_valid` | `sha256sum -c verification/checksums.txt` passes relative to the backup root |
| `file_present:*` | `metadata/contract_info.json` and `state/contract_state.json` exist and are non-empty |
| `json_valid:*` | Both required files parse as JSON (`python3` preferred, `jq` fallback; if neither is installed a **warning** is emitted and the check is skipped) |
| `dry_run_restore` | Only with `--dry-run`: staging structure and checksums are re-verified, a marker is written, and success is reported |

**No network calls are made and nothing is deployed by the verifier.** Extraction happens in a temporary directory that is removed on exit. `--dry-run` is strictly a staging restore rehearsal.

## 3. Running the verifier locally

```bash
# Verify a single archive (reports written next to the archive)
./scripts/verify-backup.sh --backup backups/nebula_backup_20260428_120000.tar.gz

# Positional form, explicit report directory, and restoration dry run
./scripts/verify-backup.sh backups/nebula_backup_20260428_120000.tar.gz \
  --dry-run --report-dir reports/

# Machine-readable output on stdout, quiet progress
./scripts/verify-backup.sh -b backup.tar.gz --json --quiet

# Help
./scripts/verify-backup.sh --help
```

Options:

| Option | Meaning |
| --- | --- |
| `-b`, `--backup <path>` | Archive to verify (also accepted as the first positional argument) |
| `-r`, `--report-dir <dir>` | Output directory for reports (default: directory containing the archive) |
| `-d`, `--dry-run` | Perform the staging-only restoration rehearsal and write a marker |
| `-j`, `--json` | Print the JSON report to stdout and suppress progress output |
| `-q`, `--quiet` | Suppress informational lines (failures are still printed) |
| `-h`, `--help` | Show usage |

Exit codes: `0` all checks passed, `1` one or more checks failed, `2` invalid usage.

## 4. Report format

For each run the following files are written to `--report-dir`:

- **`backup-validation-report.md`** — human-readable summary with status, timestamp, archive path/size/SHA256, a check table, and errors/warnings arrays.
- **`backup-validation.json`** — machine-readable report:

```json
{
  "status": "pass",
  "timestamp": "2026-04-28T02:04:11Z",
  "archive": {
    "path": "backups/nebula_backup_20260428_020000.tar.gz",
    "absolute_path": "/srv/nomad/backups/nebula_backup_20260428_020000.tar.gz",
    "size_bytes": 524288,
    "size_human": "512K",
    "sha256": "<sha256-of-archive>"
  },
  "dry_run": true,
  "duration_seconds": 2,
  "checks_passed": 16,
  "checks_failed": 0,
  "checks": [
    { "name": "gzip_integrity", "status": "pass", "details": "gzip -t passed" }
  ],
  "errors": [],
  "warnings": []
}
```

- **`backup_status.prom`** — Prometheus exposition-format status file:

```
backup_success{archive="nebula_backup_20260428_020000.tar.gz"} 1
backup_last_success_timestamp 1777351451
backup_duration_seconds 2
backup_size_bytes 524288
backup_verified_timestamp 1777351451
```

On a failed verification `backup_success` is `0` and `backup_last_success_timestamp` is `0`, which immediately satisfies the `BackupFailed` / `NoRecentBackup` alert expressions. `backup_verified_timestamp` always records the time of the current attempt.

- **`restore-dry-run.marker`** — written only for a passing `--dry-run`; contains `dry_run=pass`, the archive path, SHA256, and timestamp. It is evidence that a rehearsal completed.

## 5. CI integration

`.github/workflows/backup.yml` runs daily at 02:00 UTC and on `workflow_dispatch`:

1. Checkout, create `backups/` and `backups/verification-reports/`.
2. Run `scripts/backup.sh` with contract/RPC/Horizon secrets.
3. Upload the archive to S3 when AWS credentials are configured (`actions/upload-artifact@v4` is always used for the GitHub artifact).
4. **Verify integrity**: `./scripts/verify-backup.sh --backup "$LATEST_BACKUP" --report-dir backups/verification-reports --dry-run`. The script's non-zero exit fails the step.
5. **Explicit gate**: a separate step reads `backup-validation.json` with `jq` and fails the job unless `status == "pass"`, printing every recorded error as a GitHub Actions error annotation.
6. Upload the validation report and `backup_status.prom` as artifacts (`backup-validation-<run>`, `backup-status-<run>`) for the monitoring exporter and operators.
7. Slack success/failure notifications are preserved.

`monthly-drill` (a scheduled run) downloads the backup artifact with `actions/download-artifact@v4`, runs `verify-backup.sh --dry-run`, gates on the drill report, generates `drill-report.md`, uploads it as an artifact, and notifies Slack.

> Note: the workflow no longer references `scripts/restore.sh --verify-only`; that path was relied upon previously and is superseded by the standalone verifier.

## 6. Alerting integration

Alerts are defined in `monitoring/backup-monitoring.yml` and `monitoring/prometheus/alert-rules.yml`:

| Alert | Expression | Meaning / response |
| --- | --- | --- |
| `BackupFailed` | `backup_success == 0` (for 5m) | A verification or backup run failed. Check `backup-validation-report.md`, `backup.log`, then follow the recovery runbook. |
| `NoRecentBackup` | `(time() - backup_last_success_timestamp) > 172800` | No successful verification in 48 hours. Check the cron/workflow schedule, S3 upload, and exporter pickup of `backup_status.prom`. |
| `BackupDurationHigh` | `backup_duration_seconds > 1800` | Verification/backup is taking unusually long; inspect Horizon latency and archive size. |
| `BackupSizeAnomaly` | Size deviates > 50% from the 7-day average | Investigate for truncated exports or unexpected state growth. |
| `RecoveryFailed` | `recovery_success == 0` | A restore (or drill) reported failure. Escalate immediately; see the recovery runbook. |

The monitoring exporter scrapes the published `backup_status.prom` (the CI artifact `backup-status-<run>`) and maps these metric families into the alert rules above. Because the status file is written on both success and failure, the alerts have a reliable signal even when a run aborts early.

## 7. Dry-run drills

A dry run is a restoration rehearsal with a hard safety boundary:

- Extracts the archive into a temporary staging directory.
- Re-verifies structure, required files, and checksums.
- Writes `restore-dry-run.marker` and a passing validation report.
- **Never** contacts Horizon/RPC, never invokes the Stellar CLI for deployment, and never modifies chain state.

Run one locally before a real restore or as part of an incident review:

```bash
./scripts/verify-backup.sh --backup <archive.tar.gz> --dry-run --report-dir drill-reports
```

The monthly CI drill uses the same command and fails the job if the report status is not `pass`.

## 8. Troubleshooting

| Symptom | Likely cause | Action |
| --- | --- | --- |
| `FAIL: gzip_integrity` | Truncated or bit-flipped archive; interrupted upload | Re-download from S3/IPFS, re-run verifier; compare archive SHA256 with the upload record. |
| `checksums_present` fails | Archive produced by an older tool or checksums file removed | Rebuild the backup with `scripts/backup.sh` (it always writes checksums). Do not treat a missing checksum file as OK. |
| `checksums_valid` fails with `FAILED open or read` | A listed file is absent from the archive | Inspect `tar -tzf` output; restore from another backup. |
| `json_valid:*` fails | Corrupted/partially written snapshot | Re-run backup; inspect Horizon responses. |
| `WARN: Neither python3 nor jq ...` | Minimal runner image | Install `python3` or `jq` to enable JSON validation; the rest of the checks still run. |
| `FAIL: path_safety` | Archive contains absolute paths or `..` entries | Do not extract; treat as untrusted and re-create the backup. |
| `NoRecentBackup` fires but backups exist | Exporter is not reading `backup_status.prom` | Verify the `backup-status-<run>` artifact is published and that `backup_last_success_timestamp` is non-zero. |
| CI gate fails with "report is missing" | Backup step failed before verification | Check the backup step logs and secrets (RPC/Horizon/contract id). |

When verification fails or a restore is required, follow the incident procedures in:

- [Disaster Recovery runbook](runbooks/incident-response.md)
- [Backup & Recovery README](BACKUP_RECOVERY_README.md)
